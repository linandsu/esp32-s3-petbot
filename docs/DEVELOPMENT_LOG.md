# 小狗固件开发记录

> 本文档记录项目的重要功能变更、实现结果、排查过程和遗留问题。以后每完成一个大功能，必须在交付前同步更新本文档。

## 项目基线

- 目标板型：`bread-compact-wifi`
- 芯片：ESP32-S3
- 显示屏：1.3 英寸 OLED，128×64
- 固件框架：ESP-IDF 5.5.4
- 当前烧录端口：COM5
- 小狗 MAC：`DC:B4:D9:1B:F9:28`
- 当前局域网控制地址：`http://10.225.183.165/`（DHCP 地址可能变化）

## 2026-07-22：OLED 表情与休眠显示优化

### 完成功能

- 对话状态下根据中性、聆听、开心、伤心、愤怒等状态显示对应表情。
- 开机阶段保留官方初始化、扫描 Wi-Fi、连接 Wi-Fi 和连接服务器页面。
- 真正联网并完成初始化后才进入呼呼大睡页面。
- 休眠表情增加轻微上下浮动，模拟打瞌睡。
- 锁屏时间放大并移到中间偏上位置，日期和星期上移，适配 128×64 OLED。
- 表情切换改为在同一显示锁内完整提交，避免暴露未完成的中间帧。

### 遇到的问题

- 切换表情、进入休眠和开机联网时，会短暂闪出默认的两只眼睛。
- 官方 `neutral` 更新会在休眠页面切换过程中覆盖自定义睡眠表情。
- 旧实现通过定时轮询设备状态，存在约 200 ms 的状态同步窗口。

### 解决办法

- 将隐藏旧表情、调整眼睛尺寸、显示配件和切换页面合并到一次 LVGL 锁操作中。
- 给应用状态机增加直接状态监听，取消依赖轮询的显示切换延迟。
- 在进入 Idle 的同一个状态转换中直接显示睡眠页面，阻止后续中性表情抢画面。
- 将启动页面、对话表情页、睡眠页和时间锁屏划分为互斥页面模式。

### 验证结果

- 编译通过并烧录 COM5。
- 开机时先显示联网初始化流程，完成后进入睡眠表情。
- 对话、睡眠、锁屏之间能够按设备状态切换。

### 未解决问题

- OLED 动画的最终观感仍依赖实体设备主观确认；后续新增表情时必须继续遵守原子切换规则。

## 2026-07-22：局域网网页控制台

### 完成功能

- 使用现有 Wi-Fi STA 模式，在同一局域网启动 HTTP 与 WebSocket 控制服务。
- 提供动作、灯光、表情、音量、睡眠、唤醒及设备状态控制。
- 网页支持手机和电脑响应式访问。
- 接口包括 `/`、`GET /api/status` 和 `/api/ws`。
- 使用 mDNS 发布 `http://xiaozhi-dog.local/`，同时在屏幕和状态接口提供真实 IP 地址。
- 网页断线后自动重连，设备重连 Wi-Fi 后控制服务自动恢复。

### 遇到的问题

- `.local` 在部分手机或 Windows 环境无法解析。
- DHCP 分配的 IP 可能在更换网络或路由器重启后变化。
- 高频 WebSocket 状态广播会使连续滑块命令排队，影响实时控制。

### 解决办法

- 保留 `.local` 作为可选入口，同时始终返回并显示当前真实 IP。
- 建议在路由器中按 MAC 固定 DHCP 地址。
- 对实时灯光更新采用“最多一个在途请求，只保留最新值”的合并策略。
- 高频灯光更新不再逐次广播整份状态，由请求确认和周期状态同步共同闭环。

### 验证结果

- 当前可通过 `http://10.225.183.165/` 访问。
- 新版网页、WebSocket 命令和状态接口均已在实机验证。
- 实时灯光更新确认延迟约为 49～74 ms。

### 未解决问题

- 手机不支持 mDNS 时仍需使用 IP 地址。
- 当前网页不设密码；同一 Wi-Fi 内的其他设备也可以控制小狗。
- 未实现公网访问，这是当前安全边界，不计划通过端口映射开放。

## 2026-07-22：网页睡眠与唤醒对话闭环

### 完成功能

- 网页“进入睡眠”执行真实语音休眠，不再只切换表情。
- 网页“唤醒对话”重新打开音频通道、启动语音处理并进入自动聆听。
- 睡眠请求会阻止延迟到达的 TTS 再次把设备唤醒。
- 状态接口增加聆听模式、音频通道和语音处理运行状态。

### 遇到的问题

- 原网页唤醒调用 `StartListening()`，该入口固定使用手动停止聆听模式。
- 用户说完话后服务器一直等待停止命令，直到点击睡眠才开始处理并回答。
- 页面虽然显示“聆听中”，但无法证明麦克风处理链路真正运行。

### 解决办法

- 新增网页专用唤醒入口，使用设备默认的自动停止聆听模式。
- 根据 Idle、Speaking、Listening 和音频通道状态执行完整唤醒流程。
- 睡眠时发送停止聆听、终止说话、关闭连接中的音频通道并回到 Idle。
- 状态接口公开 `listening_mode`、`audio_channel_open` 和 `voice_processing` 用于闭环检查。

### 验证结果

- 唤醒后状态为自动聆听、音频通道开启、语音处理开启、小狗站立。
- 睡眠后状态为 Idle、语音处理关闭、小狗趴睡。
- 连续完成“睡眠→唤醒→睡眠→再次唤醒”测试。

### 未解决问题

- 声学效果仍受麦克风安装、增益和环境噪声影响；软件状态正常不能完全代替现场说话测试。

## 2026-07-22：语音查询网页控制地址

### 完成功能

- 新增 `self.web_control.get_url` 工具。
- 用户询问网页控制地址时，小智读取当前真实 IP 并语音回答。
- OLED 独立覆盖显示控制网址约 15 秒，结束后不破坏原有状态页面。

### 遇到的问题

- 普通通知内容在睡眠表情页会被隐藏。
- 对话状态变化可能立即把普通通知切回表情页。

### 解决办法

- 增加独立的控制网址覆盖层，并将其移动到显示最前层。
- 使用带代数标识的延迟隐藏任务，防止旧任务隐藏新网址。
- 工具每次动态读取当前 STA IP，不在回答中写死地址或仅返回 `.local`。

### 验证结果

- 固件中确认包含新增 MCP 工具，设备烧录后正常联网。
- 当前工具返回的地址与 `/api/status` 中的控制地址一致。

### 未解决问题

- 语音是否准确触发工具依赖云端模型的工具选择，仍需用实体设备进行自然语言测试。

## 2026-07-22：实时灯光与新增灯效

### 完成功能

- 颜色选择后立即生效，删除“应用颜色”按钮。
- 亮度滑块拖动时实时生效，不中断当前灯效。
- 更换颜色时保留当前呼吸、闪烁、流水或霓虹灯效。
- 新增流水灯、霓虹灯和彩虹灯。
- 常亮、呼吸、闪烁、流水和霓虹支持网页及语音指定颜色。
- 彩虹灯自动变色，但支持实时亮度调整。
- 新增统一语音工具 `self.lamp.set`。

### 遇到的问题

- 原呼吸灯和闪烁灯固定使用白色，且只运行有限次数。
- 设置亮度必须重新应用颜色，并会终止动态灯效。
- 快速拖动滑块会产生大量旧命令，出现松手后继续追赶旧值的问题。
- 旧灯效任务被直接删除，快速切换时存在旧任务覆盖新灯效的风险。

### 解决办法

- 将基础颜色、亮度和灯效拆分为独立状态。
- 动态灯效循环实时读取当前颜色和亮度。
- 使用原子代数停止旧灯效任务，旧任务发现代数变化后自行退出。
- 浏览器合并连续更新，只保留最后的颜色和亮度。
- 高频更新不立即广播完整设备状态，减少 WebSocket 队列压力。

### 验证结果

- 黄色呼吸灯调整为蓝色后仍保持呼吸模式。
- 调整亮度后灯效类型保持不变。
- 流水、霓虹、彩虹、闪烁和关闭命令状态均验证成功。
- 最终版本已编译并烧录 COM5。

### 未解决问题

- 不同灯罩和 WS2812 批次会影响颜色观感，颜色校准尚未实现。
- 当前每路灯带为 4 颗 LED，流水效果精细度受硬件数量限制。

## 2026-07-22：GPIO10 触摸模块手势控制

### 完成功能

- 停用 GPIO47，将触摸模块输入迁移到 GPIO10。
- 配置为高电平有效：触摸有输出，松手无输出。
- 单击：开机连接 Wi-Fi 阶段进入配网；正常状态切换完整唤醒与休眠。
- 双击：从站立、坐下、左转、右转和挥手中随机执行一个安全动作。
- 长按 1.2 秒：切换灯光开关；开灯时恢复关灯前的颜色、亮度和灯效。
- 首次长按开灯默认使用白色常亮。

### 遇到的问题

- 原 GPIO47 逻辑是低电平有效的“按住说话”，与新模块的高电平点动输出不匹配。
- 如果单击继续调用旧的 `ToggleChatState`/手动聆听流程，可能重新引入唤醒后无法自动处理语音的问题。
- 原 `TurnOff()` 通过清空 RGB 和亮度实现关灯，会丢失恢复所需的灯效参数。
- 单击、双击和长按必须互斥，不能一次触摸执行多个功能。

### 解决办法

- GPIO10 按键对象明确设置为高电平有效、长按阈值 1200 ms。
- 单击直接按真实状态调用 `WakeForWebControl()` 或 `EnterSleepMode()`。
- 灯光控制器增加独立的上次有效状态快照和 `TogglePower()` 入口。
- 使用 ESP IoT Button 自带状态机区分单击、双击和长按；组件会在双击窗口结束后再确认单击，长按进入独立状态。
- 双击动作池排除持续前进、后退、趴睡和停止。

### 验证结果

- GPIO10 配置、三种手势回调和灯光恢复代码编译无警告。
- 固件已成功烧录 COM5，设备正常启动和联网。
- 软件验证唤醒后为自动聆听和语音处理开启，休眠后语音处理关闭。
- 五个安全动作均可通过统一动作入口执行。
- 已在关灯前保存亮度 73 的蓝色霓虹灯，供实体长按测试恢复效果。

### 未解决问题

- GPIO10 触摸的实际灵敏度、单击/双击节奏和 1.2 秒长按手感需要实体模块确认。
- 必须确认触摸模块输出为 3.3V，GPIO10 不可承受 5V 输入。
- 实体测试若出现误触，需要根据模块抖动情况再调整滤波或手势时间窗口。

## 2026-07-22：网页端更换唤醒词

### 完成功能

- 在局域网“小狗控制台”的“设备设置”区域增加唤醒词设置，不改动 Wi-Fi 配网页面的职责。
- 支持四个中文预设词：你好小智、小爱同学、嗨小欧、你好小瑞。
- 支持输入 2～8 个纯中文汉字作为自定义唤醒词，并使用本地 `pinyin-pro` 自动生成、允许修正识别拼音。
- 唤醒词模式、显示文字、预设模型和自定义拼音保存到 NVS；保存成功后网页显示倒计时并自动重启生效。
- `/api/status` 和 WebSocket 状态增加 `wake_word`，WebSocket 增加统一的 `wake_word.set` 命令和结构化校验错误。
- 资源分区同时打包四个 WakeNet9 模型、中文 MultiNet7 模型和 FST，不覆盖字体、表情等原有资源。
- 配置损坏、目标模型缺失或自定义命令初始化失败时，自动回退“你好小智”。
- 固件内嵌网页和拼音库，修改唤醒词不依赖外网或第三方生成网站。

### 遇到的问题

- 本机全局 ESP-IDF 环境仍指向旧版 5.3.1，和项目实际使用的 5.5.4 不一致。
- 首次实机启动时，`afe_config_init()` 会从资源列表自动填入前两个 WakeNet；即使随后覆盖第一个模型，第二个模型仍会同时参与识别。
- 手机窄屏下，网页头部和部分网格控件的固有宽度造成横向溢出。
- NVS 写入最初沿用会触发致命断言的封装，不适合作为可恢复的网页配置写入路径。
- 网页在等待保存时继续接收设备状态广播，旧状态会重新点亮旧预设按钮，并清空尚未保存的自定义输入。
- 原先用于“保存后重启”的 ESP 定时器在实机上保持 `restart_pending`，但没有实际执行重启，导致保存后看起来没有反应。

### 解决办法

- 编译和烧录显式使用 ESP-IDF 5.5.4 的 Python、工具链、CMake 和 Ninja 路径。
- 根据 NVS 中的选择精确查找目标 WakeNet；同时将 `wakenet_model_name_2` 显式清空，确保运行管线只启用当前选择的一个预设模型。
- 自定义模式切换到 `mn7_cn`，校验中文字符数、拼音音节数和小写字母格式，并检查 MultiNet 命令注册和更新的返回值。
- NVS 改为直接执行打开、写入、提交和关闭，失败时向网页返回错误，不因配置写入失败重启或崩溃。
- 为手机布局补充 `min-width: 0`、窄屏网格和横向溢出约束。
- 网页增加唤醒词草稿状态：用户选择预设、切换到自定义或输入拼音后，状态广播只更新“当前已生效”信息，不再覆盖草稿；保存成功后才重新接受设备状态。
- WebSocket 未连接时禁止静默提交，明确提示请求没有发送；服务端返回保存结果后，网页显示重启倒计时。
- 用独立的延时重启任务替代失效的网页服务定时器，先发送成功响应，等待 3 秒后执行设备重启。

### 验证结果

- 页面测试：390 px 手机视口下 `scrollWidth == clientWidth == 375 px`，无横向滚动；中文输入可自动生成拼音，非法混合字符会禁止保存。
- HTTP 测试：`/` 返回 200 且包含唤醒词设置；`/vendor/pinyin-pro.min.js` 返回 200，大小 323244 字节；`/api/status` 正确返回当前预设、模型和重启状态。
- 编译结果：ESP-IDF 5.5.4 编译成功；`xiaozhi.bin` 为 `0x302cb0` 字节，应用分区剩余 `0xed350` 字节（24%）。
- 烧录结果：COM5 完整烧录成功，应用和 4115636 字节资源镜像均通过 SHA 校验。
- 实机启动：Wi-Fi、云端 MQTT、OLED、本地网页服务和语音引擎均正常启动；控制台地址为 `http://10.225.183.165/`。
- 模型验证：资源列表包含四个 WakeNet、`mn7_cn` 和 `fst`；最终 AFE 管线为 `WakeNet(wn9_nihaoxiaozhi_tts,)`，第二模型为空。
- 回归验证：设备当前为“小爱同学”时，选择“你好小瑞”并等待状态刷新，页面只保留“你好小瑞”一个草稿高亮；输入“你好小狗”后等待刷新，中文输入和自动生成的 `ni hao xiao gou` 均保留，保存按钮可用。
- 自定义词实机闭环：保存“你好小狗”后，接口回读为 `custom / ni hao xiao gou / fallback=false`；设备启动日志确认 `mn7_cn` MultiNet7 已初始化。
- 自动重启实机闭环：恢复“小爱同学”后，网页收到“设置已保存，3 秒后重启”响应；设备重新联网，接口回读为 `preset / wn9_xiaoaitongxue / restart_pending=false`。

## 2026-07-22：统一唤醒词检测阈值

### 完成功能

- 控制台“唤醒词设置”新增检测阈值滑杆，当前值以 `0.40`～`0.95` 显示。
- 预设 WakeNet 和自定义 MultiNet 共用同一份阈值配置；切换模式或词语不会再自动改变阈值。
- 阈值与唤醒词一起保存到 NVS，并通过 `/api/status` 的 `wake_word.threshold` 返回给网页。
- 预设模式启动时通过 AFE 的 WakeNet 阈值接口应用配置；自定义模式启动时通过 MultiNet 阈值接口应用相同配置。

### 遇到的问题

- WakeNet 的有效下限为 `0.40`，而 MultiNet 理论上可低至 `0.00`；若按各自范围设计，切换模式会造成同一数值被悄悄改写。

### 解决办法

- 按统一配置约束为两者都支持的交集 `0.40`～`0.95`，默认 `0.63`。
- 网页明确提示：数值越低越容易唤醒，同时误唤醒概率也更高。

### 验证结果

- ESP-IDF 5.5.4 编译通过，`xiaozhi.bin` 为 `0x3039c0`，应用分区剩余 23%。
- 固件已成功烧录 COM5，应用与资源镜像均通过校验。
- 实机状态接口回读当前阈值为约 `0.63`；设备当前用户自定义词保持不变，语音引擎正常进入 MultiNet 模式。

### 未解决问题

- 阈值对实际唤醒率与误唤醒率的最佳平衡仍需结合当前麦克风、距离及环境噪声进行实体语音测试。

### 未解决问题

- 每个预设词和自定义词的实际唤醒率、误唤醒率仍需在设备麦克风、使用距离和现场噪声下逐项说话验证。

## 2026-07-23：舵机动作串行化与触摸双击顺序

### 完成功能

- 将舵机改为单一、可取消的动作执行器；网页、语音、触摸和自动休眠不再分别创建竞争同一组舵机的动作任务。
- GPIO10 双击固定按“坐下 → 挥手 → 坐下”循环；动作执行或请求等待期间双击只会停止并恢复站立。
- 新动作会取消旧动作并先恢复安全站立姿势；停止、唤醒和低电保护不会排队等待旧动作结束。
- 自动休眠只保留伸懒腰过渡，完成后直接趴睡；移除了挠痒、大伸展和长时间待机随机身体动作。
- 网页状态新增 `dog_action_running`，控制台在动作名称后标明“执行中”。

### 遇到的问题

- 原实现会为转向、行走和每条腿的角度缓动分别创建任务；连续双击可令多个任务同时写入同一舵机角度，导致抖动或卡住。
- 原休眠过渡在动作任务内使用长延时，唤醒请求只能排队，无法即时打断。

### 解决办法

- 使用动作代次和 20ms 可取消等待切片；新请求立即使旧动作在下一次舵机步进或等待切片退出。
- 四腿目标角度由单一执行任务逐步同步推进，不再产生遗留的单腿任务。

### 验证结果

- ESP-IDF 5.5.4 编译通过，`xiaozhi.bin` 为 `0x306ed0`，应用分区剩余约 23%。
- 已烧录 COM12；应用和资源镜像均完成写入并通过哈希校验，设备自动复位成功。
- 联网后 `/api/status` 返回 `dog_action=sleep`、`dog_action_running=false`，确认新动作状态接口可用。
- 通过控制台停止持续转向后，设备随状态机进入休眠过渡并最终回到 `dog_action=sleep`、`dog_action_running=false`，确认不会留下后台动作任务。
- 连续双击、动作中双击停止和休眠动作中触摸/语音唤醒的实体机械手感仍建议逐项确认。

### 未解决问题

- 无；实体动作节奏和舵机机械极限需在烧录后按实际机体观察。

## 2026-07-23：修复前进后退卡死（步态被误改为逐度缓动）

### 完成功能

- 修复上一次“舵机动作串行化”改造中引入的步态回归：前进、后退卡死（观感为卡顿/几乎不动），左右转节奏与原版不符。

### 遇到的问题

- 原版 `walkfront`/`walkBack`/`turnLeft`/`turnRight` 是逐条腿直接跳变到目标角度，腿间只停顿 40ms，一套四腿姿势约 160ms 完成。
- 上一次改造把 `Walk`/`Turn` 的每个姿势都改成经过 `MoveToAngles`：四腿同步、1°一步的缓动。角度差较大的姿势（如转向 40°~80°）单帧就要走 40~80 次、每次 8~10ms，导致整套步态被拖慢 5~10 倍，看起来像卡死。
- 逐项换算比对后确认左右转的四腿角度组合本身与原版完全一致，问题只出在移动方式（缓动 vs 直接跳变），不需要改角度。

### 解决办法

- 新增 `PetDog::SetPoseDirect()`，还原原版直接跳变方式：依次设置四条腿角度，每条腿间隔 40ms，不做逐度缓动，同时保留可取消检查（每一步都能被新动作请求打断）。
- `Walk()` 与 `Turn()` 改为调用 `SetPoseDirect()`，恢复原版节奏；`Stand`/`Sitdown`/`Sleep`/`Wave`/`StretchThenSleep` 保持使用 `MoveToAngles` 逐度缓动，因为原版这些动作本来就是通过并行逐度缓动实现的，行为一致，不需要改动。
- 单一动作执行器与可取消代次（generation）机制未改动，双击动作互斥的修复继续有效。

### 验证结果

- ESP-IDF 5.5.4 编译通过，`xiaozhi.bin` 为 `0x306f60`，应用分区剩余 23%。
- 已烧录 COM12，应用与资源镜像（4115636 字节）均通过哈希校验，`Hard resetting via RTS pin...` 后设备自动复位。
- 前进、后退、左转、右转的实机手感和节奏待用户实体确认。

### 未解决问题

- 无；用户实体测试确认前进、后退、左右转均已恢复正常。
